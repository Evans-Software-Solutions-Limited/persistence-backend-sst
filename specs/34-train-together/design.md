## D1. Existing foundation

Solo start currently writes SQLite locally; completion queues `/sessions/record` with stable client IDs. The record pipeline deduplicates per athlete and applies statistics/PR effects. The `gym_buddy` entitlement currently permits everyone and must change. Existing friendship/gym-buddy schema fields do not establish a working friend product. These are local-checkout observations, not deployed verification.

## D2. Session protocol and authorization

Keep solo drafts local. Explicit promotion creates a server-backed session; initial connectivity and acknowledgement are required. Proposed entities: session (state, writer generation, revision), participants/consent, expiring invitations, shared exercise plan, athlete sets, ordered commands and participant completion mappings.

Authenticated API operations cover create, join request/approval, snapshot, command submission, leave, writer transfer and finalize. Every command validates actor, entitlement, membership, status, allowed fields, unique command ID and expected revision. Broadcast acknowledged revisions only. Reconnect loads a snapshot/missing revisions; stale writes require explicit reconciliation. Central entitlement rules include paid grants, coach catalog identifiers and grace periods.

A single nominated logger is the initial design candidate, not an approved constraint. Transfer increments a writer generation so queued old-writer commands cannot replay. Both-phone editing requires per-athlete authority and conflict rules before sign-off. Losing eligibility preserves save/exit while stopping further paid collaboration.

## D3. Mobile, offline and completion

Pure domain state machines and session/realtime/storage ports sit behind application commands; HTTP/WebSocket and SQLite adapters implement them. Containers orchestrate consent, invitation/discovery, active session, sync status and recovery presenters.

Persist pending commands locally with command IDs/revisions; the guest displays stale status during disconnect. Do not silently apply generic last-write-wins to shared sets. Leaving preserves acknowledged personal work. Completed personal results become immutable to partners. Finalize through the existing record pipeline with unique session/participant mappings; retry unfinished participants only and suppress the former solo enqueue after promotion.

## D4. Social discovery and sharing

Friendship APIs implement pending/accepted/removed/blocked state. Discovery returns bounded, paginated joinable summaries respecting audience, expiry, blocks and host approval. Store selected venue/place references and coarse search coordinates separately from private session content; geocoding provider/cost remains open. Report endpoints and moderation handling precede public discovery.

Template-sharing APIs expose a sanitized plan snapshot and explicit copy action; exclude athlete sets, private notes and health data. Link revocation affects future access, not already accepted independent copies. Membership for these supporting actions requires a product decision.

## D5. Transport and release compatibility

Spike managed realtime versus authenticated AWS WebSockets on access revocation, ordering, reconnection, latency and operational cost. Keep the protocol transport-independent. Built-in WebSocket does not inherently require a native library, but OTA suitability depends on the actual released runtime and update configuration.

The inspected mobile app lacks `expo-location` and direct location permission configuration. Adding foreground GPS requires a new owner-built binary and permission copy. Manual venue/town selection does not need device-location access. Never initiate native/EAS/mobile builds without Brad explicitly authorizing that specific build.

## D6. Evidence and release

Validate unauthorized subscriptions, invite replay, entitlement combinations, independent weights/PRs, reconnect, writer loss, early leave, partial finalization, blocks, expiry, copy privacy and solo regressions. Use two physical phones with an interrupted gym session and record latency evidence. Ship the agreed integrated feature together behind rollout controls; engineering stages are not separate product releases. No date commitment before the protocol spike and product decisions.

## D7. Research-driven design questions (proposed)

Trace AC9–10 to the [research protocol](./RESEARCH-2026-09-15.md). Distinguish common plan exercise IDs from athlete-specific execution/override records; an individual substitution or skipped set must not rewrite the shared plan or partner history. Independent rest state is per athlete. Resolve concurrent edit authority alongside this model before implementation.

Measure the pair journey using minimal session/pair identifiers: invite, open, eligibility result, approval, recorded personal work, successful completion for both and repeat session. Separate true paid-gate rejection, technical failure, abandoned invitation and unavailable partner. Do not record exercise details in the product-growth events. Compare total logging effort across both people so moving all work to the host is not mislabeled an improvement. Nearby search success requires venue/time density and must be evaluated separately from private pair use.

## D8. Executable protocol — supersedes D2–5 proposals

All following routes are new under the existing authenticated API, implemented in `microservices/core/src/application/together/` and mounted in `microservices/core/src/api.ts`. Actor derives exclusively from verified JWT, never body IDs. IDs are UUIDs except opaque invitation/place/cursor tokens. Dates are UTC ISO strings. Authorize every request and subscription delivery; never trust a client entitlement. Use the central subscription catalog and entitlement resolver, including effective grants/grace rules; update `gym_buddy` consistently on both platforms. Do not infer eligibility from display text.

Every mutation requires `Idempotency-Key` UUID. Persist `(actor, route, key, requestHash, result)` atomically with effects for the feature data lifetime; same key/body returns the original authorized result, different body returns 409 `IDEMPOTENCY_MISMATCH`. Replays after revoked access return 403 without exposing prior partner payloads. Responses: `{data, revision?}`; paginated reads `{data:[],nextCursor:null|string}`. Errors `{error:{code,message,currentRevision?}}`: 400 invalid schema, 401 unauthenticated, 403 `FORBIDDEN`/`PAID_REQUIRED`/`DELEGATION_REVOKED`, 404 inaccessible resource, 409 `VERSION_CONFLICT`/`SESSION_FULL`/`INVALID_STATE`/`ACTIVE_SESSION_EXISTS`, 410 `INVITE_EXPIRED`/`CURSOR_EXPIRED`, 429 rate limit with Retry-After. Never reveal blocked relationships through error details. Enforce bounded arrays (100 exercises, 100 sets per exercise), nonnegative finite weights, integer reps 0–10000 and validated existing exercise IDs.

`plan={name,exercises:[{planExerciseId,exerciseId,order,targetSets,targetReps?}]}`. `ownExecution={exercises:[{planExerciseId,substituteExerciseId?,skipped,sets:[{setId,reps,weightKg,completed}]}]}`; imported solo work belongs only to creator. Guest starts empty execution against shared plan, never copies completed sets. Snapshot contains state, hostId, revision, planVersion, plan, authorized participants (userId, status, ownRevision, delegationGeneration, execution) and pending personal completion status. Apply-to-both creates two explicit commands with separate authority/acknowledgements; no implicit copy.

Command `{commandId,expectedVersion,target:{kind:"plan"|"execution",athleteId?},delegationGeneration?,operation}`. `operation` is discriminated `replacePlan{plan}`, `upsertSet{planExerciseId,set}`, `removeSet{planExerciseId,setId}`, `substitute{planExerciseId,exerciseId|null}`, `skip{planExerciseId,skipped}`, or `rest{endsAt:null|ISO}`. Host only replaces plan. Once any participant has recorded execution for a planExerciseId, its underlying exerciseId is immutable and that reference cannot be removed; order may change. Reject a replacePlan that changes either with 409 INVALID_STATE, including when only the other participant has recorded work. Perform this check in the same transaction as plan replacement and serialize against execution writes, so concurrent first-set recording cannot bypass it. New exercise identities require new planExerciseIds; athlete substitutions remain explicit execution overrides and never rewrite acknowledged set identity or history/PR attribution. For each athlete/planExerciseId, substituteExerciseId may change or reset to null only before that athlete has acknowledged sets. After any set has been acknowledged, reject a substitute command that changes or resets the existing value with 409 INVALID_STATE; a same-value command is a no-op. Serialize substitution validation with first-set writes in the same transaction, and persist an ever-acknowledged identity-lock tombstone even if all acknowledged sets are subsequently removed; deletion cannot unlock identity for offline or replayed commands. The shared plan identity lock also derives from these persistent tombstones across participants, not merely currently present sets. Thus one exercise execution cannot retroactively reattribute prior sets by changing or clearing its substitution. Execution commands target self or an explicitly delegating active partner. Generation required for partner commands. Compare target version transactionally; each accepted command increments target and session revisions and emits `{revision,commandId,target,newVersion,operation}` through a durable outbox. Two athletes' unrelated changes can succeed without false global conflicts; same-target stale edits return 409 and require visible reconciliation, never silent last-write-wins. Ownership/entitlement/block/generation checks precede dedup response delivery.

Host loss does not elect another writer: guest keeps own logging/rest/substitution/finish; shared plan remains frozen until host returns. Session closes when both finish, or host finishes with no guest. Host finish removes discovery and invitations, but a joined partner can finish separately. Expiry/block closes collaboration and delegation immediately; own pending execution is accepted through the command route in recovery-only mode (no plan/partner edits), then finish. Event delivery filters after current authorization; sockets are disconnected on block/leave and clients purge partner cache. Commands already committed before revocation stand; later commands fail. No endpoint exposes historical or health records through this membership.

Session state is `active|closed`; participant state is `active|finalizing|saved|finished_empty`. Finish/leave atomically checks ownRevision and transitions active→finalizing, freezing that athlete's execution before enqueueing the durable job. Further edits receive 409 INVALID_STATE; retry or job recovery completes finalizing→saved (or finished_empty with no performed sets). Failure never reopens writes or loses the persisted job. Snapshot and finish response include `status:"finished_empty"` when appropriate. Rest timestamps are advisory local timers, not proof of performed exercise. Promotion and joins atomically enforce the one-active-session invariant; local unresolved drafts must be resolved before request submission.

### Durability and mobile integration

Persist local commands before optimistic display; retain ack status and target versions across restart. Reconnect fetches snapshot, reconciles command IDs and retries unchanged pending keys; stale edits require explicit compare/reapply with a new command ID. Do not automatically rebase conflicting completed sets. Finish/leave drains or explicitly resolves pending commands first. On unrecoverable permission failure preserve owner's pending work as a recoverable draft; rejected partner edits are shown to their author for correction, never silently attributed to self. Other devices recover server state, not unavailable local-only commands; disclose this limitation before switching/logout.

Promotion uses a durable local promotion marker keyed clientDraftId: timeout queries/retries same identity before solo save; after server acknowledgement disable ordinary solo completion enqueue. A transaction creates a unique `(sharedSessionId,athleteId)` finalization job and stable record client ID. Reuse the existing recording service's statistics/PR behavior, not a second implementation; write record, completion mapping and effects atomically or with durable idempotent outbox stages. Server retries crashed jobs; GET snapshot exposes status; repeated finish returns the same history. Never require both athletes to commit together. A no-work athlete gets a finished/no-history result explicitly; exactly one history applies to athletes with recorded work.

## D9. Shared social and place contracts

Together backend owns these common contracts, schema and migrations; coach discovery consumes them and must not create competing primitives. All list limits default 20/max 50; opaque cursors bind query and actor. Authenticated reads permitted to free members.

- `GET /places/search?q=...&cursor=&limit=`: q trimmed length 2–100 → paginated `Place={placeId,label,center:{latitude,longitude}}`. Center is a provider's coarse locality/venue centroid, never an athlete location. Validate lat/lon ranges. Resolver adapter/provider choice in spike; no paid account activation. `GET /places/nearby?latitude=&longitude=&cursor=&limit=` offers foreground assistance; coordinates are ephemeral, excluded from logs/analytics/storage. Persist only a deliberately selected placeId and display metadata. GPS denial/revocation always leads to manual search.
- `PUT /social/profile {discoverable:boolean}` → `{discoverable}` sets own opt-in searchable profile status (default false), without publishing sessions or health data.
- `GET /social/people?q=&cursor=&limit=`: q 2–100, opt-in public profiles only, omit blocked users; return `{userId,displayName,avatarUrl?}`. `GET /social/friends` and `/social/requests` return accepted/pending relationships respectively.
- `POST /social/requests {userId}` → `{requestId,status}`; `POST /social/requests/:id/decision {decision:"accept"|"reject"}` recipient only; `DELETE /social/friends/:userId` removes relationship bilaterally. Removal hides friends-only discoveries and revokes unused friend invitations/template offers; an already consented session remains until leave/block.
- `PUT /social/blocks/:userId {}` and `DELETE /social/blocks/:userId` → `{blocked:boolean}`. Self block invalid. Shared backend `canInteract(actorId,targetId)` checks either-direction block; used by coach contact/profile access and Together subscriptions/invites/sharing. Block strips friendship, closes shared access and hides both profiles/discovery; unblock never restores grants. Report UI can block immediately.
- `POST /social/reports {subjectUserId,context:"together"|"coach",resourceId?,reason:"harassment"|"spam"|"unsafe"|"other",details?}` → `{reportId}`; details ≤2000 characters, authorized context only. Store private moderation record; backend operations queue with staff-only access, no peer notification or report disclosure. Public discovery rollout requires named moderation ownership and documented review procedure.
- `POST /together/templates {recipientUserId,plan}` → `{shareId}`; accepted unblocked friend and both paid, store sanitized immutable plan. `GET /together/templates?cursor=&limit=` lists own sent/received shares; `GET /together/templates/:id` permitted parties only. `POST /together/templates/:id/copy {}` → `{workoutId}`; paid recipient, unique `(shareId,recipientId)` prevents duplicate retry copies. `DELETE /together/templates/:id` revokes future access, sender only; existing independent copy survives. Never include notes, sets/results or health data.

Mobile common `LocationPermissionPort` exposes `status(): granted|denied|undetermined` and `requestForeground()` with same result; `PlaceSearchPort` exposes search and nearby. Together frontend owns adapters and permission/config changes; coach frontend imports ports and reusable selector. GPS requires Brad's specifically authorized new native binary, not an OTA assumption.
