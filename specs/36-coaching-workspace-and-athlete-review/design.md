# 36 — Coaching workspace and athlete review: design

Proposed 18 September 2026. Requirements WS-1–9; implementation unchecked. Existing behaviour remains until a compatible migration and clients ship.

21 September update: W1 now has an isolated executable [schedule/prescription spike and populated migration/offline contract](W1-MODEL-SPIKE.md). It traces the existing mobile start and record interfaces and names W2 integration gates. Runtime APIs/schema are unchanged; the spike is not production compatibility proof.

## D2. Owner/self services and schedule model

One domain service accepts `{actor,owner,targetAthlete?,purpose}` from trusted route context. Self routes require actor=owner and capability; coach-target operations separately enforce role, entitlement, live relationship, data-sharing consent and seats where applicable. Actor/owner fields in client payloads never grant authority. Do not create a fake self-coach relationship or populate coach roster entries to implement self-planning.

Proposed owner APIs: `GET/POST /users/me/programs`, `GET/PATCH /users/me/programs/:id`, `POST /users/me/programs/:id/schedule`. Reuse existing workout authoring services and introduce aliases only where necessary. Lists/read enforce ownership; create/edit/schedule enforce the new capability. Programme ID alone never permits reading another coach's library. Coach routes call the same domain operations with their existing guarded context. Use idempotency keys for create/schedule and expected revision for edits; shared conflict schema is delivered before parallel frontend work.

Extend spec 19 additively: `scheduleMode=cycle|explicit`, immutable programme revisions, explicit schedule entries `{entryId,dayOffset,phaseId?,workoutRevisionId}`, and versioned validated prescriptions. A workout revision captures ordered exercise IDs plus bounded per-set prescription data, original units and optional notes. User-visible week/day labels derive from dayOffset; actual dates derive from selected start date in athlete's IANA time zone. Preview before assignment confirms alignment of named weekdays. Explicit mode requires finite duration; candidate maximum is a proposed 52-week horizon (364 days), distinct from the current coach-create maximum of 104 weeks, with server-bound occurrence count and performance test before final limit selection. Multiple sessions in one day have separate ordered entry IDs. Rest days are absence of sessions plus optional labels, never phantom missed workouts.

Existing cycle definitions/indefinite materialization continue unchanged. New assignments reference a published programme revision and occurrence prescription; materialization idempotency includes assignment+entry/occurrence identity. Self assignment carries `assignmentOrigin=self`, not implied coach authority. Coach projections filter actor/relationship-owned assignments; self assignments cannot accidentally appear as coach prescriptions. All existing readers that assume trainer_id is a real coach must be audited before this origin ships.

For published changes, backend returns an impact preview and applies only selected untouched future occurrences against the expected assignment revision. Never overwrite completed, in-progress, rescheduled or athlete-overridden work implicitly. Start-session and apply-update serialize on occurrence/version; stale mobile starts receive a clear conflict and refreshed prescription. Snapshot effective load and its max/date basis at session start; %1RM can remain symbolic until a real max is available. Preserve historical units and prescriptions with logged results. Notifications use a durable outbox after commit, deduplicated on change ID.

Do not reuse spec 19's historical “tables empty” migration assumption. Plan a populated-data migration/backfill, mixed-client capability handling and rollback that retains old cycles. New clients check supported prescription/schedule versions; old clients are blocked from starting unsupported assignments with an update-required response rather than seeing a lossy fallback. Trace both existing assignment listing and session-start routes, not just the new editor. The current mobile start command writes only to local SQLite; server rejection alone cannot enforce this rule. W1 must define capability-aware assignment delivery and a cached immutable prescription/offline-start policy before implementation: an offline start pins its cached occurrence revision, later synchronization must preserve that executed snapshot, and a server-side schedule edit cannot pretend it knew an offline start had occurred. A conflicting new prescription requires explicit reconciliation, never overwriting logged work. Prevent delivery of unsupported explicit assignments to older runtimes at assignment/listing boundaries, while preserving existing cycle access. Prove stale-cache/offline-start scenarios in the spike. This compatibility spike gates full-fidelity import acceptance.

## D3. Shared training review contract

Add a pure `TrainingReviewService`, authorization adapters and explicit safe response schema. Candidate routes: `GET /users/me/training-review` for self/athlete, and `GET /trainers/me/clients/:id/training-review` for coaches. Query: bounded `from/to`, `scope=self|coach_relationship`, optional authorized relationship ID for the athlete, and display time zone. A coach can only request their own relationship scope. Self view may aggregate owned/assigned training for the athlete; it is not mirrored to a coach without existing consent and explicit scope.

Return `{scope,period,dataVersion,asOf,coverage,planAdherence,activity,progress,sharedSummary,sharedComments}`. No private notes field exists in this DTO. `planAdherence={completed,expected,rate,lateCompleted,excused,cancelled,definitionVersion}`; rate is completed/expected, or null when expected=0. Count distinct eligible occurrence IDs with due dates in the interval through the last concluded athlete-local day. Completed means one authoritative linked saved session by asOf; duplicate logs count once. Athlete-skipped and missed occurrences remain expected; coach-approved cancellation/excusal is excluded and separately counted. Future/current-day pending sessions and rest days do not enter the denominator. Late completions count but are labelled, and asOf/dataVersion explain later changes. Historical rescheduling/cancellation is audited so a retrospective period change is visible, not silent denominator manipulation. Keep gym-habit attainment separate.

Coach and athlete consume the same scoped snapshot by dataVersion; no independent client-side metric recomputation. Existing coach screens adopt this named measure without silently relabeling historical metrics. Finite and indefinite programme occurrences must be materialized through the reviewed interval before calculation; missing history produces partial coverage. Personal activity not authorized for a given coach is excluded. Offline workouts remain “awaiting sync” where locally known; server cannot invent unsent evidence.

Invalidate affected review caches after accepted session/assignment changes, using bounded reads and a maximum five-minute connected refresh target. Include stale/offline state. Revocation overrides any cache; reauthorize before response and summary-job result delivery. No need to introduce the Together realtime transport just to display progress.

## D4. AI and feedback

Self summary generation `POST /users/me/training-review/summary`; coach shared generation through the scoped coach review path. Capability/quota validated server side; coached athlete viewing a shared result does not need Premium Plus. Automatic shared generation, if enabled, is funded by the coaching benefit and bounded (proposed once per concluded day when evidence changes), not by every screen refresh. It stops when the coaching relationship/entitlement/consent no longer permits it.

Cache identity includes audience (`self|shared_relationship|coach_private`), subject, authorized scope, reporting period, dataVersion and prompt/model version. Shared prompts use only safe DTO evidence; private notes are excluded before inference. Sharing old coach-facing AI text is prohibited. Summaries explain trends/limitations with metric references; no unsupported health judgments or automatic load changes. On missing data/provider failure show facts and an unavailable/stale summary, never an invented fallback. One shared snapshot serves both parties. Private coach AI remains separate and labelled.

Proposed `POST /training-reviews/:id/comments` body `{text,expectedReviewVersion}` with idempotency key, bounded length and explicit shared audience. Only the athlete and that authorized coach may read/post. Use existing communication infrastructure if the audit finds a suitable thread; otherwise a minimal review-linked comment service, not a full chat product. Escaped plain text and existing notification preferences apply. Private-note sharing creates a new explicit shared comment; it does not toggle old records to public. Coaches cannot delete athlete history during offboarding.

## D5. UI and release

Web workspace uses a responsive navigation shell and table/calendar editor, separating API containers from presenters. Share TypeScript contracts/pure mapping and validation with mobile; do not force mobile rendering components into the browser. Premium Plus sees My training with Plan, Progress and Review. Coached athletes see From my coach/shared review beside their assigned programme; clients with multiple coaches select the relevant relationship. Coach Clients → athlete shows the same shared panel plus clearly private coach-only areas. Show author/source and data freshness, not role jargon.

Backend contracts and entitlement tests first; then parallel web shell/editor, mobile self/review containers and AI projection work. Scheduling migration and prescription compatibility are one backend owner's responsibility. No native binary for web alone; microphone/document selection features follow spec 22's owner-build gate. Validate screenshot flows and keyboard/screen-reader use, plus two-user, two-coach, downgrade/revocation and old-runtime tests. No rollout claims until real device/backend evidence exists.
