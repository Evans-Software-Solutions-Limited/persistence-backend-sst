# W1 — Explicit programmes and executed prescriptions

21 September 2026. PER-5 / FND-01 initial implementation. Native Persistence capabilities inspired by the comparison research; no Relay integration. This is an executable design spike, not a shipped assignment feature or an applied migration.

## Evidence and boundaries

`microservices/core/src/application/programs/spikes/explicitSchedule/model.ts` is deliberately unconnected to API routes. Its inputs are trusted typed fixtures, not validated external requests. The colocated `__tests__/fixtures.ts` describes six weeks starting Monday 21 September: Mon/Wed/Fri, week 3 Mon/Fri only, week 4 deload, two distinct Friday sessions in week 6. It preserves set-level variations, symbolic percentages, kg/lb, RPE/RIR, tempo, rest, duration and distance. Rest labels are metadata, not counted occurrences. JSON round trip plus materialization has asserted dates, prescriptions and independent snapshots.

The tests also exercise the **existing** `buildOccurrences` function for finite and indefinite cycles. New functions model capability delivery, selected future updates, compare-and-swap conflict, protected work, cached local start and late reconciliation. These are deterministic interleavings, not a real SQL concurrency test or SQLite integration test. Passing them does not authorize full-fidelity import acceptance.

## Proposed additive persistence contract

- Programme revision: immutable ID, programme ID, schema version, mode, author, publication timestamp, finite duration for explicit schedules. Cycle rows continue to use their existing schedule until deliberately republished.
- Workout prescription revision: immutable ID, version and ordered exercise/set payload with original units and source provenance. Unsupported constructs remain review errors; they must not disappear into free text or guessed loads.
- Explicit entry: stable entry ID, programme revision ID, day offset, same-day order, phase/rest metadata and workout revision ID. Uniqueness is revision plus entry ID; a programme edit retains entry IDs for unchanged logical sessions. Separate occurrence ID distinguishes repeated assignments of the same entry.
- Assignment: origin (`coach` or `self`), owner/athlete, published revision, selected start date, IANA time zone, optimistic version. Do not infer `self` from a null coach: a deleted coach already produces that value. Audit every coach-reader assumption before introducing self-origin.
- Occurrence: assignment plus stable entry, due date, effective prescription revision, lifecycle and explicit override/reschedule flags. A programme publication can yield a mix of revisions across its occurrences; do not rewrite protected occurrences just to make a parent pointer uniform.
- Executed prescription: session plus exact occurrence/revision and immutable snapshot, including resolved %1RM weight **and** measured max/unit/date basis where available. No max means symbolic prescription with actual performance logged separately. Existing sessions remain `legacy_unknown` for historical prescription provenance; current templates are not evidence of past intent.

Use bounded server validation before persistence: real ISO dates, supported versions, finite numeric loads and max evidence, legal set counts/ranges, unique entry/order identities, finite schedule horizon/occurrence limits and recognized units. The spike checks entry identities/offsets only. Final limits (including the proposed 364-day horizon), rounding policy, timezone changes and workout-deletion retention require integration decisions/tests. Date-only fixtures demonstrate calendar arithmetic; they do not validate arbitrary IANA zones.

## Populated migration and rollback contract

1. Inventory counts and foreign-key health for programmes, programme assignments, ad-hoc assignments, swaps, completed sessions and deleted-coach attribution. Capture finite/indefinite, active/completed/skipped and null-owner examples in a disposable database fixture. Never assume the tables are empty.
2. Generate additive schema migrations from Drizzle. Create revision/entry/execution tables, nullable references and mode/origin support without changing existing IDs, current indexes or cycle semantics. Keep read/write feature flags off. Batch any large backfill by stable key with resumable checkpoints; validate new constraints separately to avoid long blocking operations.
3. Existing rows read as legacy cycle without any new prescription assertion. Backfill mode/provenance idempotently; a snapshot of a currently mutable template may only be labelled `captured_at_migration`, never `prescribed_at_session_start`. Leave completed and existing active records without manufactured historical revisions. Preserve ad-hoc rows and coach-null attribution. No schedule regeneration, due-date recalculation or log reassignment in this migration.
4. Shadow-read and compare legacy output and counts before enabling writes. Test repeat migration/backfill, interruption/resume and writes during backfill on the populated fixture. Reconcile all counts and verify historical actual sets byte-for-byte. Test self-origin separately from existing null coach rows.
5. Deploy capability-aware backend reads before any explicit assignment writes. Ship capable clients and their SQLite migration, then enable new assignments only for supported paths. Existing users can keep starting legacy cycles. No lossy down-conversion of new schedules into the cycle DTO.
6. Rollback disables new publication and explicit assignment creation; preserve immutable revisions, execution snapshots and queued uploads. Keep compatibility read/record handling deployed until outstanding offline sessions drain; rolling back to an old backend that cannot read explicit records is unsafe. Destructive down-migration is disallowed once new rows exist. Reversal before activation may remove unused additive structures after verifying they are empty.

This migration contract is proposed for PR review; **no SQL migration/backfill has been generated or run**. Database-level populated migration proof belongs to W2.

## Offline start, publication and delayed logging

Cache a complete immutable, athlete-owned occurrence prescription with version and issuance proof, not only a workout ID. Legacy delivery suppresses unsupported explicit cards and returns an update-required state where the DTO permits; no supported-version claim means legacy capability. Backend enforcement must cover direct reads, lists and start affordances. New clients reject unsupported cached versions before creating a session. Existing cycle caches continue unchanged.

Local start pins the cached occurrence plus max evidence in the same SQLite transaction as the active session. Online start acknowledgement and publication use a transaction/compare-and-swap on the occurrence/assignment version: if acknowledgement wins, publication excludes it; if publication wins, the online client refreshes or makes an explicit choice. The spike models the exclusion and stale expected-version checks, not actual locking.

Offline start may legitimately use an older cached revision after publication. The server cannot know it happened. On delayed record, validate that the revision was issued to that athlete for that occurrence; accept the performed workout without rewriting its prescription. If it matches the current revision, complete that occurrence. If it differs, persist a `needs_reconciliation` link and keep the new plan pending until an explicit resolution decides whether the old execution satisfies it. Preserve both versions, result and decision audit. Device time is evidence, not authorization to overwrite current state. Never reject/discard actual results merely because the plan changed.

Production record must preserve `(userId, clientSessionId)` idempotency and detect a reused ID with a different snapshot/body. Replays return the same durable result; simultaneous devices cannot attach two sessions to one occurrence without a visible conflict. The spike demonstrates deterministic repeat reconciliation only; it does not implement durable idempotency, issuance proof, revocation or duplicate-device arbitration. Revoked coach access cannot read cached client data, while the athlete retains their own performed history.

## Acceptance evidence and remaining gates

Run from `microservices/core`:

```sh
bun run test:unit src/application/programs/spikes/explicitSchedule/__tests__/model.test.ts --coverage.include=src/application/programs/spikes/explicitSchedule/model.ts
```

Initial result: **16 tests passed; model.ts 100% statements, branches, functions and lines.** Fixtures cover six-week dates, DST/leap-date arithmetic, changing units/loads, irregular frequency, deload, same-day distinct entries, legacy cycles, unsupported clients, detached snapshots, absent max, selected publish protection, stale publisher and late offline execution.

W1 executable design is implemented for PR review. W2 remains gated on real schema/migration fixtures, external-payload validation and limits, explicit occurrence delivery across all readers, client SQLite persistence/rehydration, SQL race/idempotency tests, authorization/revocation and two-device delayed-sync tests. No claim is made that assignment→start→log works with this model in the running app. Full programme imports, self authoring and client assignment must wait for that proof.
